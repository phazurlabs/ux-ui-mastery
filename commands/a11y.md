# A11y — Accessibility Audit

Deep accessibility audit against WCAG 2.2 AA standards with code fixes for every violation found. This is not a surface scan — it covers semantic HTML, ARIA implementation, keyboard navigation, color contrast (including APCA), focus management, screen reader compatibility, cognitive accessibility, and produces corrected code for every finding.

**Accepts**: Code (file paths or pasted), screenshot description, or component reference.

---

## Audit Protocol

### Step 0: Gather Context

1. **Implementation code**: The artifact to audit
2. **Platform**: Web (HTML/CSS/JS), iOS (SwiftUI/UIKit), Android (Compose/XML)
3. **Target compliance level**: WCAG 2.2 AA (default) or AAA if requested
4. **User context**: Are there known users with specific accessibility needs?
5. **Prior Sumi outputs**: Consume `/qa` findings (accessibility section) if available

### Step 1: Semantic HTML Analysis

**Heading hierarchy**:
- [ ] Proper heading levels (h1-h6) with no skipped levels
- [ ] Single h1 per page (or per landmark region in SPA)
- [ ] Headings describe section content accurately
- [ ] Heading levels reflect visual hierarchy

**Landmark regions**:
- [ ] `<header>` / `role="banner"` — page header
- [ ] `<nav>` / `role="navigation"` — navigation areas (with aria-label if multiple)
- [ ] `<main>` / `role="main"` — primary content (exactly one per page)
- [ ] `<aside>` / `role="complementary"` — supplementary content
- [ ] `<footer>` / `role="contentinfo"` — page footer
- [ ] All content is within a landmark region

**Form structure**:
- [ ] Every input has an associated `<label>` (via `for`/`id` or wrapping)
- [ ] Related inputs grouped with `<fieldset>` and `<legend>`
- [ ] Required fields indicated both visually and programmatically (`aria-required` or `required`)
- [ ] Input types match content (`type="email"`, `type="tel"`, `inputmode`)
- [ ] Autocomplete attributes present where applicable

**List structure**:
- [ ] Lists of items use `<ul>`, `<ol>`, or `<dl>` appropriately
- [ ] Navigation links in `<ul>` or `<ol>` lists
- [ ] Definition lists for term-definition pairs

**Table accessibility**:
- [ ] Data tables have `<caption>` or `aria-label`
- [ ] Column/row headers use `<th>` with `scope` attribute
- [ ] Complex tables use `headers` attribute for cell-header association
- [ ] Layout tables avoided (use CSS grid/flex instead)

**Semantic element usage**:
- [ ] `<button>` for actions, `<a>` for navigation (not interchangeable)
- [ ] `<dialog>` for modals (or equivalent ARIA)
- [ ] `<details>`/`<summary>` for disclosure widgets
- [ ] No `<div>` or `<span>` as interactive elements without ARIA roles
- [ ] `<time>` for dates/times with `datetime` attribute

For each violation, provide the current code and the corrected code.

### Step 2: ARIA Implementation Audit

**First Rule of ARIA**: No ARIA is better than bad ARIA. Check for:

**Redundant ARIA**:
- `role="button"` on a `<button>` element (redundant)
- `role="link"` on an `<a>` element (redundant)
- `role="navigation"` on a `<nav>` element (redundant)
- Flag and remove all redundant ARIA

**Required ARIA attributes**:
- Every `role` has its required attributes (e.g., `role="checkbox"` needs `aria-checked`)
- Every `aria-labelledby` and `aria-describedby` references a valid ID
- Every `aria-controls` references an existing element
- Every `aria-owns` references existing elements

**ARIA states and properties**:
- `aria-expanded` on expandable controls (accordions, dropdowns, menus)
- `aria-selected` on selectable items (tabs, listbox options)
- `aria-pressed` on toggle buttons
- `aria-current="page"` on current navigation item
- `aria-invalid="true"` on invalid form fields
- `aria-busy="true"` during loading states
- `aria-hidden="true"` on decorative/hidden content (verify it IS actually hidden from all users)

**Live regions**:
- `aria-live="polite"` for non-urgent dynamic content updates
- `aria-live="assertive"` for urgent notifications (errors, alerts)
- `role="alert"` for error messages
- `role="status"` for status messages
- `aria-atomic` and `aria-relevant` set appropriately

**Custom widgets**:
- Tabs: `role="tablist"`, `role="tab"`, `role="tabpanel"`, `aria-selected`, arrow key navigation
- Menu: `role="menu"`, `role="menuitem"`, `aria-expanded`, arrow key + Home/End navigation
- Combobox: `role="combobox"`, `aria-expanded`, `aria-activedescendant`, `aria-autocomplete`
- Tree: `role="tree"`, `role="treeitem"`, `aria-expanded`, arrow key navigation
- Dialog: `role="dialog"`, `aria-modal="true"`, `aria-labelledby`, focus trap

For each ARIA issue, provide the specific fix with code.

### Step 3: Keyboard Navigation Audit

**Tab order**:
- [ ] Tab sequence follows visual reading order (left-to-right, top-to-bottom for LTR)
- [ ] No positive `tabindex` values (only `0` or `-1`)
- [ ] All interactive elements reachable by Tab
- [ ] Skip-to-content link as first focusable element
- [ ] Tab does not enter elements with `aria-hidden="true"`

**Focus visibility**:
- [ ] All focusable elements have visible focus indicators
- [ ] Focus indicator has >= 3:1 contrast ratio against adjacent colors
- [ ] Focus indicator is at least 2px thick (WCAG 2.2 2.4.13 recommended)
- [ ] Focus indicator encloses the entire component (not partial)
- [ ] Custom focus styles don't rely on color alone (use outline, border, or shadow)
- [ ] `:focus-visible` used to show focus only on keyboard interaction (not mouse clicks)

**Focus management**:
- [ ] Opening a modal moves focus to the modal (first focusable element or the modal container)
- [ ] Closing a modal returns focus to the trigger element
- [ ] Focus is trapped inside open modals (Tab cycles within)
- [ ] Escape key closes modals, popovers, dropdowns
- [ ] Deleting an item moves focus to a logical next element (not lost)
- [ ] Route changes move focus to the new content (or page top)

**Keyboard patterns for interactive widgets**:
- [ ] Arrow keys navigate within composite widgets (tabs, menus, radio groups)
- [ ] Enter/Space activate buttons and links
- [ ] Space toggles checkboxes
- [ ] Enter submits forms
- [ ] Home/End navigate to first/last items in lists
- [ ] Type-ahead in listboxes and menus

**Keyboard traps**:
- [ ] No unintentional focus traps (user can always Tab out)
- [ ] WYSIWYG editors, date pickers, and embeds have documented exit mechanism
- [ ] Third-party iframes don't trap focus

For each keyboard issue, provide the specific fix with code.

### Step 4: Color Contrast Audit

**WCAG 2.2 AA minimum contrast ratios**:

| Element Type | Minimum Ratio | Standard |
|-------------|---------------|----------|
| Normal text (<24px / <18.66px bold) | 4.5:1 | WCAG 1.4.3 |
| Large text (>=24px / >=18.66px bold) | 3:1 | WCAG 1.4.3 |
| UI components and graphical objects | 3:1 | WCAG 1.4.11 |
| Focus indicators | 3:1 | WCAG 2.4.11 |

**For each text element**:
- Calculate contrast ratio (foreground vs. background)
- If on gradient or image, calculate against lightest and darkest areas
- Flag any ratio below the threshold
- Provide the corrected color with exact hex value that meets the ratio

**APCA (Advanced Perceptual Contrast Algorithm) scores** — the future standard:
- Lc 75+ for body text
- Lc 60+ for large/bold text
- Lc 45+ for UI components and non-text
- Lc 30+ minimum for any visible element

Calculate and report APCA Lc values alongside WCAG ratios for forward-compatibility.

**Non-color indicators**:
- [ ] Links distinguished from text by more than color (underline, icon, or weight)
- [ ] Error states indicated by more than red color (icon, text, border)
- [ ] Required fields indicated by more than color (asterisk, text)
- [ ] Chart/graph data distinguished by more than color (patterns, labels, shapes)
- [ ] Status indicators use more than color (icons, text labels)

**Color blindness considerations**:
- Test against protanopia (red-blind), deuteranopia (green-blind), tritanopia (blue-blind)
- Flag red/green combinations used for success/error
- Flag any color pair that becomes indistinguishable under any type of color blindness

### Step 5: Screen Reader Compatibility

**Image accessibility**:
- [ ] Informative images have descriptive alt text (what the image communicates, not what it looks like)
- [ ] Decorative images have `alt=""` or `aria-hidden="true"`
- [ ] Complex images (charts, infographics) have extended descriptions
- [ ] SVG icons have `aria-hidden="true"` if decorative, or `role="img"` + `aria-label` if informative
- [ ] Image captions associated with images via `<figure>` and `<figcaption>`

**Link and button text**:
- [ ] Link text is descriptive out of context ("Read the accessibility guide" not "Click here")
- [ ] Multiple links with the same text go to the same destination
- [ ] Button text describes the action ("Delete message" not "Delete")
- [ ] Icon-only buttons have `aria-label` describing the action

**Dynamic content**:
- [ ] Content added to the DOM is announced (via live region or focus management)
- [ ] Content removed from the DOM does not leave orphaned focus
- [ ] Infinite scroll announces new content loading
- [ ] Toast notifications use `role="alert"` or `aria-live`
- [ ] Loading states announce start and completion

**Reading order**:
- [ ] DOM order matches visual order
- [ ] CSS `order`, `flex-direction: row-reverse`, or `grid` doesn't create reading order mismatches
- [ ] Visually hidden content is in logical position in DOM
- [ ] Off-screen content is properly hidden (`display: none`, `visibility: hidden`, or `aria-hidden`)

**Text alternatives**:
- [ ] Audio content has text transcript
- [ ] Video has captions and/or audio description
- [ ] Emojis have text alternatives or are decorative

For each screen reader issue, provide the specific fix with code.

### Step 6: Cognitive Accessibility

Accommodations for users with ADHD, dyslexia, autism, cognitive disabilities, and age-related decline:

**ADHD considerations**:
- [ ] No auto-playing media or animations that cannot be paused
- [ ] No infinite scroll without clear progress indicators
- [ ] Important actions require confirmation (prevent impulsive errors)
- [ ] Task progress is saved automatically (no lost work from distraction)
- [ ] Clear visual hierarchy reduces decision fatigue
- [ ] Notifications can be deferred or batched

**Dyslexia considerations**:
- [ ] Font size >= 16px for body text
- [ ] Line height >= 1.5x font size
- [ ] Paragraph width <= 80 characters (ideally 45-75)
- [ ] Left-aligned text (not justified — uneven word spacing is harder)
- [ ] Sans-serif fonts preferred (or dyslexia-friendly fonts available)
- [ ] Sufficient contrast without pure black on pure white (#000 on #fff can cause visual stress)
- [ ] Letter spacing >= 0.12em, word spacing >= 0.16em (WCAG 1.4.12)

**Cognitive load reduction**:
- [ ] Instructions are clear and concise
- [ ] Error messages explain what went wrong AND what to do next
- [ ] Forms are broken into logical steps (not one long page)
- [ ] Default values provided where possible
- [ ] Consistent navigation and layout across pages
- [ ] No time limits on tasks (or they can be extended)
- [ ] Help text available in context (not just documentation)

**Autism considerations**:
- [ ] Predictable navigation and interaction patterns
- [ ] No ambiguous or metaphorical language in UI text
- [ ] Clear expectations before actions ("This will send the email to 5 people")
- [ ] Ability to customize sensory experience (reduce animations, change colors)

**Age-related considerations**:
- [ ] Touch targets >= 44px (ideally 48px)
- [ ] Text size can be increased without breaking layout
- [ ] Clear contrast between interactive and non-interactive elements
- [ ] Simple, familiar interaction patterns

For each cognitive accessibility issue, provide the specific fix.

### Step 7: Motion and Animation Accessibility

- [ ] `prefers-reduced-motion` media query respected
- [ ] Reduced motion alternative provided (not just removed — provide non-animated alternative)
- [ ] No flashing content >3 flashes per second (WCAG 2.3.1 — seizure risk)
- [ ] Auto-playing animations can be paused, stopped, or hidden
- [ ] Parallax scrolling has a non-parallax alternative
- [ ] Scroll-triggered animations respect reduced motion preference

### Step 8: Compliance Summary and Code Fixes

For EVERY finding, provide:

1. **WCAG criterion**: Specific success criterion (e.g., 1.4.3 Contrast Minimum)
2. **Level**: A, AA, or AAA
3. **Severity**: Critical (blocks access), Serious (major barrier), Moderate (inconvenience), Minor (best practice)
4. **Element**: Exact element or component affected
5. **Current code**: What exists now
6. **Fixed code**: Corrected implementation
7. **Explanation**: Why this matters (which users are affected and how)

## Quality Gates

The output MUST include:
- [ ] Semantic HTML analysis covering headings, landmarks, forms, lists, tables, and element semantics
- [ ] ARIA audit checking redundancy, required attributes, states, live regions, and custom widgets
- [ ] Keyboard audit covering tab order, focus visibility, focus management, widget patterns, and traps
- [ ] Color contrast with both WCAG ratios AND APCA Lc values for every flagged element
- [ ] Non-color indicator check for links, errors, required fields, and data visualization
- [ ] Screen reader compatibility covering images, links, dynamic content, reading order, and text alternatives
- [ ] Cognitive accessibility covering ADHD, dyslexia, cognitive load, autism, and age considerations
- [ ] Motion accessibility covering reduced-motion, seizure risk, and auto-play
- [ ] Code fix for EVERY finding (current code + corrected code)
- [ ] WCAG criterion cited for every finding
- [ ] Severity level for every finding with impact explanation
- [ ] Compliance summary table with counts by category and severity
- [ ] Manual testing checklist for issues that require human verification

The output MUST NOT include:
- Findings without code fixes — every issue must include the corrected code
- Vague recommendations ("improve contrast") — provide exact color values
- WCAG criterion without specific number (not "contrast issue" but "1.4.3 Contrast Minimum")
- Missing categories — all 7 audit areas must be covered even if clean
- ARIA recommendations that violate the First Rule of ARIA (no ARIA is better than bad ARIA)
- Cognitive accessibility ignored — this is a full audit, not just technical compliance

## Auto-Fix Engine

When the user runs `/a11y fix` or requests fixes, generate corrected code for EVERY finding. Not just recommendations — actual corrected code that can be copy-pasted.

### Fix Category 1: Contrast Fixes

For every text/background pair that fails WCAG AA (4.5:1 for normal text, 3:1 for large text):
- Calculate the current contrast ratio using APCA or WCAG 2.x formula
- Adjust the text color OR background color (whichever requires less visual change)
- Output the corrected CSS/Tailwind with the exact color value
- Show: `before → after` with contrast ratios
- If oklch is used, adjust the L (lightness) channel to hit the target ratio
- If Tailwind is used, map to the nearest compliant shade (e.g., `text-gray-500` → `text-gray-700`)

### Fix Category 2: ARIA Fixes

For every missing or incorrect ARIA attribute:
- Buttons without accessible names → add `aria-label` with descriptive text inferred from context
- Images without alt → add `alt` with description inferred from context, or `alt=""` for decorative
- Dynamic content without live regions → add `aria-live="polite"` or `aria-live="assertive"`
- Modals without dialog role → add `role="dialog"` and `aria-modal="true"`
- Tabs without tablist → add full `role="tablist"`, `role="tab"`, `role="tabpanel"` structure
- Custom dropdowns → add `role="listbox"`, `role="option"`, `aria-expanded`, `aria-selected`
- Toggle buttons → add `aria-pressed="true/false"`
- Provide the complete corrected JSX/HTML for each component

### Fix Category 3: Keyboard Navigation Fixes

- Missing focus styles → add `focus-visible:ring-2 focus-visible:ring-offset-2 focus-visible:ring-[primary-color]` (Tailwind) or equivalent CSS
- Missing tab order → add/adjust `tabIndex` values
- Non-focusable interactive elements → add `tabIndex={0}` and `onKeyDown` handlers for Enter/Space
- Modal without focus trap → generate a focus trap implementation (using `useEffect` for React or equivalent)
- Missing skip-to-content link → generate the full skip link component:
  ```tsx
  <a href="#main-content" className="sr-only focus:not-sr-only focus:absolute focus:top-4 focus:left-4 focus:z-50 focus:px-4 focus:py-2 focus:bg-white focus:text-black focus:rounded-md focus:shadow-lg">
    Skip to main content
  </a>
  ```
- Dropdown without Escape-to-close → add keyboard handler
- Missing arrow key navigation for lists/menus

### Fix Category 4: Semantic HTML Fixes

- `<div>` used as button → replace with `<button>` (preserving styles)
- `<div>` used as link → replace with `<a>` with proper `href`
- Missing heading hierarchy → restructure headings (h1 → h2 → h3, no skips)
- Missing landmark regions → wrap in `<header>`, `<nav>`, `<main>`, `<aside>`, `<footer>`
- List of items in `<div>`s → replace with `<ul>`/`<li>` or `<ol>`/`<li>`
- Form inputs without labels → add associated `<label>` elements

### Fix Category 5: Color & Visual Fixes

- Color as only indicator → add icon, text label, or pattern as secondary indicator
- Error states using only red → add error icon (exclamation) + descriptive text
- Success states using only green → add checkmark icon + descriptive text
- Links distinguished only by color → add underline (`underline underline-offset-2`)
- Charts/graphs using only color → add patterns, labels, or texture differentiation

### Fix Category 6: Motion & Cognitive Fixes

- Missing reduced-motion support → wrap animations in `@media (prefers-reduced-motion: no-preference)` or add `motion-safe:` Tailwind prefix
- Auto-playing content → add pause/stop controls
- Flashing content → remove or reduce below 3 flashes per second
- Complex instructions → simplify language, add step-by-step breakdown
- Information overload → suggest progressive disclosure patterns
